结果已经显示：关闭两次 W/x 完整读回后，校验耗时大幅下降，而权重复制和 FPGA 等待时间基本相同。另外，第二次运行的 CPU 参考计算和其余前向计算也更快了；我会把这部分变化单独列出，避免把总加速都归因于读回开关。**这一步已经验证了预期效果：关闭两次 W/x 完整读回后，每次前向计算约节省了 970 ms；FPGA 的运算量和执行时间基本没有变化。** 可以把当前版本保存为“读回校验可切换”的软件基线。

不过，整次前向从 2239.840 ms 降到 1026.302 ms，其中还有其他阶段变快的影响，需要分开看。

**1. 正确性检查通过，两个模式执行了相同数量的任务。**

两份日志都是：

```

这与模型的 6 层一致：

两次运行都正常到达计时汇总。按照你提供的程序，任何一次 Q/K/V 逐位比较失败都会退出，因此本次两种模式的 144 次调用都通过了结果检查。

`cmp` 没有输出，也表明两份生成文本相同。这确认了**当前模型、提示词和这 8 次前向范围内**，关闭输入读回没有破坏计算结果。

**2. 读回开关的收益很清楚。**

下面统一使用“每次前向的毫秒数”比较，避免混淆累计时间和平均时间：

**3. 实测完整前向快了约 2.18 倍，但不能全部归因于读回开关。**

根据日志：

0.516262 → 0.977517 tok/s

```

两者采用的计时范围不同，所以倍率不同是可以解释的。

需要特别注意：完整前向减少约 `1214 ms`，而加速器 API 减少约 `969 ms`。另外约 `244 ms` 的变化，主要来自 CPU 参考计算和其余前向计算。

你的模型权重通过 `mmap()` 访问，第一次和后续进程运行可能受到文件页缓存、缺页、CPU 频率、调度和缓存状态等影响；现有数据不足以确定具体原因。

> 本次对照中，关闭两次 W/x 完整读回，使加速器 API 每次前向减少约 969 ms；完整前向实测加速约 2.18 倍，其中还包含其他阶段耗时变化。

正式记录稳定性能前，建议用同样的模型和参数，再按：

```text

```

运行一轮，分别保存日志。重点检查 `CPU reference` 和 `remaining_forward` 是否仍有明显波动，同时确认驱动里约 `970 ms` 的节省可以重复出现。

**4. 下一步可以实施“权重常驻共享 DDR”，预期收益现在有了依据。**

在当前 `perf` 模式中：

```text
完整前向：       1026.302 ms
W 复制：          167.743 ms，约占 16.34%
START_to_DONE：   665.830 ms，约占 64.88%
```

因此，减少重复权重复制是一个明确、可测量的下一步。

假设权重复制耗时能够从每次前向中完全移除，其他阶段不变，暂不计一次性加载开销，则：

```text
新的前向耗时约为：
1026.302 - 167.743 = 858.559 ms

对应加速比约为：
1026.302 / 858.559 ≈ 1.20 倍
```

这是根据当前分项统计得到的估计，实际收益还要实测；初始化加载时间也需要单独记录。

你的模型需要常驻的 Q/K/V 权重规模是：

```text
每个矩阵：
288 × 288 × 4 = 331,776 字节 = 324 KiB

全部 6 层 Q/K/V：
6 × 3 = 18 个矩阵

总计：
18 × 331,776 = 5,971,968 字节 ≈ 5.70 MiB
```

这些矩阵加上保护区，可以放进当前 W 区到 x 区之间的共享 DDR 空间。

实现时有一个关键点：**不能只把现有 W 复制循环关闭。** 当前所有矩阵轮流使用同一个 `W_PHYS` 缓冲区，下一个矩阵会覆盖上一个矩阵。权重常驻需要：

1. 为 18 个 Q/K/V 矩阵分配各自的共享 DDR 地址。
2. 初始化阶段分别复制一次，并完成加载校验。
3. 每次 Q/K/V 调用选择对应矩阵的物理地址，配置到 W 地址寄存器。
4. 每次仍然复制 x、启动 FPGA、读取 y，并保留 CPU 结果比较。
5. 分别统计一次性权重加载时间和推理阶段耗时。

这一步可以使用当前驱动已经支持的 W 地址配置接口，**通常不需要修改 RTL**。FPGA 每次 GEMV 仍然从 DDR 读取权重，因此主要减少的是 HPS 重复复制 W 的时间。

最后，从这次统计也能看出更长期的优化方向：`perf` 中 CPU 完成全部 Q/K/V 参考计算约需 `18.212 ms/forward`，当前加速器 API 约需 `840.007 ms/forward`。这说明当前 FPGA Q/K/V 路径的耗时仍明显高于同次运行中的 CPU 参考计算；这还不是独立的纯 CPU 推理基准，但足以说明后续硬件执行路径仍有较大优化空间。
